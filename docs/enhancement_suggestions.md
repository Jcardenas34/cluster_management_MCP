## 1. Job Result Retrieval + LLM Summarization

**The gap:** `submit_spark_job` fires and forgets. The LLM never sees the output. This is the
single biggest missing piece in the current agentic loop.

**What to build:** A `get_job_results(output_file)` tool that SSHes into the master after a job
completes, reads the output file, and returns the raw data. The LLM can then interpret it in
natural language.

**Example interaction after this is built:**
> "Run a 1000-trial simulation with 5 attackers vs 3 defenders, then tell me the win rate and
> average battle length."

The LLM submits the job, fetches the results, and narrates them — a complete agentic loop.

**Implementation sketch:**
```python
@mcp.tool()
def get_job_results(output_file: str = "risk_results.txt") -> str:
    """
    Read the output file from the last Spark simulation job on the master node.
    Returns the raw file contents for the LLM to interpret.
    """
    return _ssh_run(MASTER_HOST, f"cat {SPARK_JOB_DIR}/{output_file}")
```

**Why it matters:** Turns the agent from a job launcher into a full reasoning loop. The demo
goes from "job submitted" to the LLM narrating simulation statistics in natural language.

## 2. Pre-Submission Resource Advisor

**The idea:** Before submitting a job, the agent checks live cluster health (CPU, memory, nodes up)
and automatically recommends — or warns against — the requested parameters. If memory is at 85%
it suggests reducing `slices` or `batches`. If a worker is down it warns the job will run degraded.

**What to build:** A `recommend_job_parameters(...)` tool that queries `get_cluster_summary()`
internally and returns either a green light or an adjusted parameter set with a reason.

**Example interaction:**
> "Submit a 10,000-trial simulation."
> Agent: "Worker 192.168.1.42 is currently down and master CPU is at 91%. I recommend reducing
> slices from 100 to 40 and trials to 5,000 until the cluster recovers. Proceed anyway?"

**Implementation sketch:**
```python
@mcp.tool()
def recommend_job_parameters(
    trials: int,
    batches: int,
    slices: int,
) -> dict:
    """
    Inspect current cluster health and recommend safe job parameters.
    Returns a dict with 'recommended_params', 'warnings', and 'safe_to_submit'.
    """
    summary = get_cluster_summary()
    warnings = []

    if summary["nodes_up"] < summary["nodes_total"]:
        warnings.append(f"Only {summary['nodes_up']}/{summary['nodes_total']} nodes are up.")

    busiest_cpu = max(summary["cpu_load_percent"].values(), default=0)
    if busiest_cpu > 80:
        warnings.append(f"Highest node CPU is {busiest_cpu:.1f}% — consider reducing slices.")
        slices = max(10, slices // 2)

    busiest_mem = max(summary["memory_used_percent"].values(), default=0)
    if busiest_mem > 85:
        warnings.append(f"Highest node memory is {busiest_mem:.1f}% — consider reducing batches.")
        batches = max(10, batches // 2)

    return {
        "recommended_params": {"trials": trials, "batches": batches, "slices": slices},
        "warnings": warnings,
        "safe_to_submit": len(warnings) == 0,
    }
```

**Why it matters:** The difference between a *launcher* and an *intelligent orchestrator*. Shows
the LLM reasoning about cluster state before acting — the core value proposition of putting an
LLM in the loop.

## 3. Kafka Topic Monitoring Tools

**The gap:** The Raspberry Pi Kafka broker is existing hardware that the MCP server is completely
blind to. It is a significant part of the physical stack and is currently unused by the agent.

**What to build:** A small set of tools using the `kafka-python` library:
- `list_kafka_topics()` — what topics exist on the broker
- `get_topic_lag(topic, consumer_group)` — how far behind consumers are
- `get_kafka_broker_health()` — broker up/down, partition counts, replication status

**Dependencies to add:**
```yaml
# environment.yml
- kafka-python>=2.0
```

**Implementation sketch:**
```python
from kafka import KafkaAdminClient
from kafka.admin import NewTopic

KAFKA_HOST = os.getenv("KAFKA_BROKER_HOST", "")

@mcp.tool()
def list_kafka_topics() -> list[str]:
    """List all topics currently registered on the Kafka broker."""
    admin = KafkaAdminClient(bootstrap_servers=f"{KAFKA_HOST}:9092", request_timeout_ms=5000)
    try:
        return list(admin.list_topics())
    finally:
        admin.close()

@mcp.tool()
def get_kafka_broker_health() -> dict:
    """Check whether the Kafka broker is reachable and return basic cluster metadata."""
    ...
```

**Why it matters:** Kafka is a marquee technology on resumes. Activates unused hardware already
in the stack. Opens the door to a future pipeline where Spark writes simulation results to a
Kafka topic instead of a flat file — a natural next step for the project.

## 4. Spark Log Retrieval + Failure Diagnosis

**The idea:** When a job fails or behaves unexpectedly the user currently has no way to ask *why*.
A `get_spark_logs(app_id, tail_lines)` tool SSHes into the master, pulls the relevant application
logs, and returns them to the LLM for diagnosis.

**What to build:**
```python
@mcp.tool()
def get_spark_logs(app_id: str = "", tail_lines: int = 100) -> str:
    """
    Retrieve Spark application logs from the master node.

    Args:
        app_id:     Spark application ID (e.g. 'app-20240101-001'). If empty,
                    returns the most recent application log.
        tail_lines: Number of lines to return from the end of the log (default 100).

    Returns stdout/stderr of the log tail — hand this to the LLM to diagnose failures.
    """
    if app_id:
        cmd = f"tail -n {tail_lines} {SPARK_HOME}/logs/*{app_id}*"
    else:
        cmd = f"ls -t {SPARK_HOME}/logs/ | head -1 | xargs -I{{}} tail -n {tail_lines} {SPARK_HOME}/logs/{{}}"
    return _ssh_run(MASTER_HOST, cmd)
```

**Example interaction:**
> "Why did my last job fail?"
> Agent calls `get_spark_logs()`, reads a Java OOM stack trace, responds:
> "The job ran out of executor memory. The worker JVM threw a `java.lang.OutOfMemoryError`
> on partition 47. Try reducing `slices` to 50 or adding `--executor-memory 1g` to extra_args."

**Why it matters:** Turns the agent into a debugging assistant. LLMs excel at parsing dense
Java stack traces and explaining root causes plainly — this is one of the highest-value things
an LLM can do in a DevOps context.

## 5. Jetson Nano GPU Monitoring & Inference Dispatch

**The gap:** The NVIDIA Jetson Nano is the most exotic and impressive piece of hardware in the
cluster and the MCP server does not know it exists.

**What to build:**

**GPU health monitoring** via `tegrastats` (Jetson-native) or a Prometheus node exporter:
```python
@mcp.tool()
def get_jetson_gpu_stats() -> dict:
    """
    Query the NVIDIA Jetson Nano for current GPU utilisation, memory, and temperature.
    Returns a dict with gpu_percent, gpu_memory_used_mb, cpu_percent, and temp_celsius.
    """
    # tegrastats outputs one line; --interval 1 --count 1 gets a single sample
    raw = _ssh_run(JETSON_HOST, "tegrastats --interval 500 | head -1")
    return _parse_tegrastats(raw)
```

**Inference dispatch** — trigger a model inference job on the Nano and return the result:
```python
@mcp.tool()
def submit_inference_job(model: str, input_path: str) -> str:
    """
    Submit an inference job to the Jetson Nano edge node.
    The Nano runs the model and returns the result or output file path.
    """
    cmd = f"python3 ~/inference/run_inference.py --model {model} --input {input_path}"
    return _ssh_run(JETSON_HOST, cmd)
```

**Add to `.env`:**
```
JETSON_HOST=192.168.x.x
```

**Example interaction:**
> "What is the Jetson's GPU utilisation right now?"
> "Run fraud inference on the latest simulation output."

**Why it matters:** The Jetson Nano running local edge inference *alongside* Spark doing
distributed simulation is an unusual and differentiated stack. GPU monitoring is a highly
relevant skill signal. Coordinating both batch compute (Spark) and edge inference (Jetson)
within a single agentic interface is a compelling architectural story for any ML-focused role.
